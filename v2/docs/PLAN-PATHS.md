# Plan — program vs profile: making deployment survivable

Written 2026-10-08, measured against `feature/input-arbiter`. **Nothing here has been changed; this is
for a verdict.** Every count below was counted rather than estimated, and where a claim is a judgement
rather than a measurement it says so.

This is not a v3 proposal. See §7.

---

## 1. The problem, and its single root cause

**`AppContext.BaseDirectory` is how every path in the app is resolved — 20 call sites across
`SealTools.Core`, `SealTools.Launcher` and all six tool projects. `Environment.GetFolderPath`,
`SpecialFolder` and `AppData` appear zero times.** The install folder *is* the data folder.

Everything below follows from that one decision:

| Symptom | Why it follows |
|---|---|
| Two publish modes (`public` / `local`) | `config/` holds shipped files *and* the player's own data, so what ships cannot be decided by the folder |
| `publish.bat` copies by an **explicit list** | There is no rule that distinguishes the two kinds, so each file is named by hand |
| An update cannot replace the folder | The folder holds `local.yaml` and ~19 MB of calibration |
| PC #2 means re-calibrating from scratch | The calibration is machine-bound *and* trapped in the install directory |
| `RELTAG=v2.14` is a literal at `publish.bat:16` | Version is maintained by hand here, in the README table, in the tag, and in `RELEASE-v2.14.md` |

The explicit list is not a style complaint — the script's own comment at `publish.bat:79-82` records the
failure it causes:

> *"This list is explicit, so a config file that is not named here does not ship — and the error a
> missing dictionary raises tells the player to copy this file, which would be an instruction to copy
> something absent."*

## 2. The classification that is missing

The fix is not "better folders". It is naming, in code, **who owns each file**:

| Class | Files today | On update |
|---|---|---|
| **Program** — regenerated by the build | `.exe`, `models/`, `attributes.yaml`, `*.example` | replace freely |
| **User state** — irreplaceable | `local.yaml` (109 KB), `calib_tuner.png` (5.2 MB), `calib_gem.png` (7.3 MB), `calib_pet.png` (6.2 MB) | **never touch** |
| **Derived** — regenerable | `logs/`, `logs/reads/`, `local.yaml.backup-*`, `local.yaml.corrupt-backup` | delete freely |

Classes 1 and 2 are currently interleaved in one `config/` folder. That interleaving *is* the deployment
problem.

## 3. The trap: `defaults.yaml` is misclassified today

It reads as a program file and ships as one — `publish.bat:77` copies it in `public` mode. But it is
**written at runtime**:

- `LauncherService.cs:704` — `public void SaveConfig() => _loader.SaveDefaults(Config);`
- `ConfigLoaderTests.cs:64` — *"SaveDefaults rewrites defaults.yaml from an explicit field list…"*
- `ConfigLoaderTests.cs:521` — *"SaveDefaults serialises the MERGED in-memory config and is called by
  the tuner, gem and…"*

So it is **user state seeded from a program template**. A plan that moved only `local.yaml` and the
calibration PNGs would leave `defaults.yaml` to be silently clobbered by the next update, or to drift
from the shipped seed. It belongs in the profile, seeded on first run, with the same merge-on-upgrade
treatment the config already applies to spammer presets.

## 4. Target layout

```
SealTools/                        <- replaced wholesale on update
  SealTools.Launcher.exe
  models/                         <- until the OCR swap embeds them (see §7)
  config/                         <- shipped templates only
    defaults.yaml.example
    attributes.yaml
    attributes.us.yaml.example
    local.yaml.example
profile/                          <- never replaced by an update
  defaults.yaml                   <- seeded from the template on first run
  local.yaml
  calib_tuner.png  calib_gem.png  calib_pet.png
  logs/
  profile.json                    <- app version + machine fingerprint
```

`profile.json` is what makes PC #2 a copy instead of a re-calibration: the file named in
[IDEAS.md](IDEAS.md) §3 as "export / import calibration", scoped to a whole folder rather than to
`local.yaml` alone.

## 5. The sequence

Each step is independently shippable. Only **D** changes anything a player can observe.

| # | Step | Size | Player-visible change | Verified by |
|---|---|---|---|---|
| **A** | Add `Paths`, with `Paths.Data` returning `AppContext.BaseDirectory`; route all 20 call sites through it | S | none | the existing suite; a grep proving zero direct `BaseDirectory` uses remain outside `Paths` |
| **B** | `Paths` prefers `profile/` when that folder exists, else today's layout | S | none | existing suite on a profile-less install |
| **C** | Export / import the profile as one file (version + machine fingerprint) | S | additive | a round-trip test: export on one layout, import on another |
| **D** | Default to `profile/`; one-time migration on first run | M | **yes** — files move | migration run against a **copy of a real install**, not a fixture |
| **E** | Program-only zip; drop the mode flag and the explicit list | S | packaging only | unzip on a clean machine with no `config/` present |
| **F** | Version from one source; build stamp written into each run log | S | additive | a log whose stamp matches the tag |

Step **A** is the one to do first and the one that makes the rest small: it is a pure seam, it cannot
change behaviour, and it turns 20 scattered literals into one place to move later.

## 6. Migration, and the risk that outranks everything else

Every existing player has `local.yaml` and the three calibration PNGs inside their **current install
folder**. If step **D** only changes where the app *looks*, it loses their calibration — the single most
expensive thing they own, and the one thing that cannot be regenerated from the repo.

The precedent for doing this safely already exists: `ConfigLoader.cs:122` `MigratePetSlots` and the
`LocalPetLegacy` read path are exactly this shape of work — read the old location, translate, write the
new, and keep the old around until the new is proven.

**Requirement for D:** the migration must run on first launch of an install that has `config/local.yaml`
beside the exe, copy (not move) the calibration and local config into `profile/`, and be idempotent.
Do not delete the old files; a player who rolls back to v2.x must not find their calibration gone.

## 7. Non-goals

- **Not a v3.** Every step lands shippably and only one is visible, so this is v2.x work. A major version
  is for a changed user-visible contract — per-window calibration and multi-account, or tool cards
  becoming an always-on scheduler — not for code that got better.
- **Not `%APPDATA%` by default.** The reason this app is pleasant to deploy today is that it is
  self-contained: unzip anywhere, USB stick included. A profile directory beside the exe keeps that and
  still gets safe updates. See the ⚑ in §8.
- **Not a rewrite of anything.** The OCR `text_fixes` table, the capture quirks, the closed-loop Arduino
  placement and the calibration geometry are the irreplaceable part and none of them are touched.
- **Not the OCR swap.** [IDEAS.md](IDEAS.md) §6 would embed the models and delete `publish.bat` step 3
  (and ~25 MB), which is a deployment win — but it must land **before** the English dictionary is built,
  so it is sequenced by that constraint, not by this plan.
- **Not the Launcher extraction.** [ANALYSIS-UI.md](ANALYSIS-UI.md) §5 owns that order.

## 8. Open questions for the player ⚑

1. **Where does `profile/` live by default?** Beside the exe (keeps the app portable, our
   recommendation) or under `%LOCALAPPDATA%` (survives a careless re-unzip into a fresh folder, but
   breaks USB portability)?
2. **Does the `local` publish mode survive?** Once the profile is separate, a `local` zip is just
   "the program zip plus a profile folder" — it may be worth keeping as a convenience, or deleting as a
   second thing to maintain.
3. **Is the update check in scope now, or later?** With a release every 2–4 days, PC #2 currently has no
   way to learn a new version exists. That is a bigger deployment win than the layout — but it is
   additive and can follow E.

## 9. What was measured, and what was only reasoned about

**Measured:** the 20 call sites and the zero `AppData` uses; the `config/` file inventory and sizes; the
two publish modes and the explicit list at `publish.bat:76-83`; `RELTAG` at line 16; the firmware zip
being separate; `SaveDefaults` writing `defaults.yaml` (`LauncherService.cs:704` plus two test comments);
the `LocalPetLegacy` / `MigratePetSlots` precedent.

**Reasoned, not measured:** that `SaveDefaults` makes `defaults.yaml` unrecoverable if clobbered on
update (it is regenerated from the *merged in-memory* config, so a shipped file replacing it loses
whatever the player had saved); the ordering claim that A makes D small; and the effort sizes, which
follow the convention in [IDEAS.md](IDEAS.md) rather than an estimate from having built it.

**Not checked:** the rest of the C# beyond the files named above, and `INSTALL.md` /
[CALIBRATION.md](CALIBRATION.md) / `USER_GUIDE.md`, all of which describe the current layout to the
player and would need updating in step E.
