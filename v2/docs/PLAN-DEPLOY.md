# Plan — frozen templates: an update that cannot cover a config

Written 2026-10-14, measured against v2.15 (`91294eb`). Every count below was counted rather than estimated, and where a claim is a judgement rather than a measurement it says so (§10).

One sentence is the whole objective: **putting new code into an install must not be able to cover the configuration that install already holds.** Everything below serves that and nothing else.

The answer in brief: the public update zip ships only program files — no file the running app writes, and no file the player is told to grow in place — so extracting an update over a folder cannot match a file the player owns; the one writer that rewrites a shipped file today (the save path behind the Tuner, Gem and Hotkeys tabs and the client switch) moves its target into `local.yaml`, which the zip has never carried; and the first launch of the updated build folds the player's already-saved values into `local.yaml`'s `settings:` block once, so the legacy defaults file stops being read instead of becoming a permanent layer. No player file moves, is renamed or is deleted. The application folder stays one copyable unit — the constraint the player fixed on 2026-10-13, that the config stays at the same root path so the folder stays easy to move — and this plan treats that as non-negotiable.

---

## 1. The problem, and its single root cause

`config/` interleaves program files with player state, and the only rule that separates the two kinds is an explicit copy list in `publish.bat` (lines 74-88). Everything else below follows from that.

| Symptom (all measured) | Why it follows |
|---|---|
| The update instruction needs manual surgery: 'Unzip the new version over the old one **except for `config\`**' (INSTALL.md:187-188) | One folder holds both kinds of file, so what ships cannot be decided by the folder |
| An overlay update silently reverts the saved Tuner / Gem / Hotkeys / game-variant settings | `publish.bat:77` ships `config/defaults.yaml`, and the running app rewrites that exact file from an explicit field list (`SaveDefaults`, ConfigLoader.cs:468-519) |
| Since v2.15 an overlay update also replaces a grown US dictionary | `publish.bat:86` copies the deliberately empty `attributes.us.yaml` with `copy /Y`, unconditionally |
| The documented 'copy `config/local.yaml` across' recipe silently weakens gem empty-detection | It drops `calib_gem_result.png`, which `GemComposer.cs:48` reads at run time as the preferred empty-slot reference |
| `local.yaml` and the four calibration PNGs survive an overlay only by accident | Their names are not in the zip; nothing names them as protected, and INSTALL.md's 'and in nothing else' (line 188) is already untrue |
| The pet feeding table is dead in every installed copy | The path is built under the root (`PetTool.cs:365`, `MainWindow.xaml.cs:3652`) and `PetFeeding.cs:49` returns an empty table when the file is absent — and the v2.15 zip's 19 entries include no `docs/` |

## 2. The classification that is missing

The fix is not better folders. It is naming, in code and in the packaging script, who owns each file.

| Class | Files | On update |
|---|---|---|
| **Program** — regenerated by the build or maintained in the repo; no runtime writer targets it; the player is not told to edit it in place | `SealTools.Launcher.exe` and the 10 native DLLs; `models/` (3 .onnx, 16.2 MB); `config/attributes.yaml` (the TW dictionary); `config/defaults.yaml.example` (the shipped reference defaults — the repo tracks the file as `config/defaults.yaml` and `publish.bat` renames it at packaging time); `config/attributes.us.yaml.example`; `config/local.yaml.example`; `docs/pet-data.csv` (newly in the zip) | replace freely |
| **User state** — irreplaceable, or measured on one machine | `config/local.yaml` (112 KB today; machine state plus the `settings:` block, which is the fold's home); `config/defaults.yaml` (the legacy values layer; folded once, §3); `config/attributes.us.yaml` (grown in place); `calib_tuner.png`, `calib_gem.png`, `calib_gem_result.png`, `calib_pet.png` (~18.9 MB together); any `config/attributes.<name>.yaml` this release does not ship — a personal dictionary named through the variant machinery, which `config/defaults.yaml:27` itself invites | never a member of the public zip, so an extract cannot reach them (the `local` zip ships them deliberately — publish.bat:67-73 — and is a development convenience, never a player's update) |
| **Derived** — regenerable; deletable without loss | `logs/` (error.log, ocr_log.jsonl, ocr_errors.jsonl, captures/, reads/, run_*); `config/<name>.<guid>.tmp` while a write is in flight; the historical manual `local.yaml.backup-*` and `local.yaml.corrupt-backup` | absent from the zip; nothing depends on their contents |

One rule replaces per-file judgement: **no archive member is a file the app writes, or a file the player is told to grow in place.** It is enforced twice — by the explicit copy list, and by a check that opens the produced zip and fails the build unless every member is on a declared program list: every `config/` member is `attributes.yaml` or `*.example`, no `attributes.*.yaml` other than the declared seeds, and the packaged `defaults.yaml.example` is byte-equal to the committed template (step 3). The check is an allow-list rather than five hardcoded names, so an unexpected member fails even when nobody thought to deny it — which is how a future `copy` line for a new writer's file gets caught. `attributes.yaml` stays in the zip because it is release-maintained program content that no writer targets; a player who edits the TW dictionary's copy accepts that the next update replaces it, and a personal dictionary belongs in a variant's own file — the machinery `config/defaults.yaml:27` points at, and where USER_GUIDE.md:565's 'edit `attributes.yaml`' line is redirected (step 3).

## 3. The trap: `defaults.yaml` is user state wearing a program file's name

It reads as a program file and ships as one (`publish.bat:77`). It is not. `SaveDefaults` (ConfigLoader.cs:468-519) re-serialises it from an explicit field list, and five actions call it: the Tuner tab's Save (MainWindow.xaml.cs:1683), the Gem tab's Save (1733), the gem calibrator's save, which writes both files (4215), the Hotkeys Save (4619), and the Setup tab's client switch (LauncherService.cs:752 then 706).

Two consequences are on the record:

- The field list has silently deleted things four recorded times — a machine's spammer presets, `gem.move_mode`, a hand-added `pet:` block, `ocr_retries` — and the code carries the history in its comments and in a reflection fence.
- On 2026-10-13 the client switch rewrote the file and the player saw a stray key in it — that is the player's report. What this checkout shows is narrower: `v2/config/defaults.yaml` has a modification time of 23:05 that day and its bytes are identical to HEAD.

So `defaults.yaml` is user state seeded from a program template, and an update that extracts that template over it reverts the player's saved values. It is also the file whose hand-written comments cannot survive a YamlDotNet rewrite, because the writer serialises an object graph and the only comments that survive are the ones the writer emits itself (ConfigLoader.cs:30-39).

The plan's answer, in three moves: on the first launch of the updated build the player's *differences* — each portable value that differs from the shipped example — are folded once into `local.yaml`'s `settings:` block (step 2, specified in §4 and §6); `defaults.yaml` leaves the zip (step 3); the app stops writing it (step 4). After that fold the file is never read again, and neither the update nor the fold ever writes it: it stays on disk as the rollback copy and the record of what the player had, until the player deletes it. (One qualification, because steps 3 and 4 may ship apart: until step 4 lands, the old writer still rewrites that file on any tab save, exactly as it does today. It is frozen — and so a true rollback copy — only once the app has stopped writing it.) Deleting it is then genuinely lossless: everything the player ever saved is in `local.yaml`. The one path back to the old behaviour is the fallback for a fold that cannot be written (read-only medium, full disk): that session keeps reading the file as a values layer and the fold retries on the next launch.

## 4. Target layout

```
SealTools/                          the whole folder is still the unit that moves
  SealTools.Launcher.exe, *.dll     program — in the zip
  models/                           program — in the zip
  docs/
    pet-data.csv                    program — newly in the zip (the pet feeding table)
  config/
    attributes.yaml                 program — in the zip (release-maintained TW dictionary)
    defaults.yaml.example           program — in the zip; never written, never hand-edited
    attributes.us.yaml.example      program — in the zip; template, method and seed
    local.yaml.example              program — in the zip; seed for local.yaml
    local.yaml                      user state — machine state + the settings: block (the fold's home)
    defaults.yaml                   user state, legacy — the fold's source; read only until it folds;
                                    absent on fresh installs; safe to delete after a successful fold (§6.9)
    attributes.us.yaml              user state — seeded from its .example on first use; grown in place
    attributes.<name>.yaml          user state — a personal dictionary this release does not ship
    calib_tuner.png  calib_gem.png
    calib_gem_result.png  calib_pet.png           user state (~18.9 MB)
  logs/                             derived — error.log, ocr_log.jsonl, captures/, reads/, run_*
```

The read rules:

- The **base** is `config/defaults.yaml.example` when it exists; when it does not — a repo checkout — it is `config/defaults.yaml`, exactly as today. If neither exists, the existing `ConfigException` ('Missing config file: ...') stays.
- The **fold**. When the example AND `config/defaults.yaml` both exist — an install that has taken the new zip — and `settings.legacy_folded` is not yet true, the legacy file is read once as a second `AppConfig` and compared against the shipped example, leaf by leaf, over exactly the leaves the legacy file itself contains. An absent key folds nothing, so a class default can never enter `local.yaml` wearing the player's name. The comparison covers the portable projection and the spammer block — the list step 2 fences — and each leaf that differs is written into **the block that leaf already belongs to in `local.yaml`**: the portable leaves into `settings:`, the spammer leaves into the existing `spammer:` block. No leaf is left without a destination, and a key that matches is not written at all, so an untouched key keeps tracking the released template.
- The fold is **one write** through the existing atomic writer, under the save gate that spans the whole read-modify-write (§6.4), and **the marker is set in that same write even when nothing differs**: a machine that never changed a value still gets `legacy_folded: true`. Without that, the fold would re-run against a later release's example and pin that release's changed defaults as the player's own — the marker is what makes "once" true, so it is written unconditionally. The legacy file's own block is normalised by the passes that already exist before it is compared — `MigrateSpammerPresets` turns a pre-presets flat `keys` into a `default` preset and the legacy `startup_step` folds into the object shape — so every leaf has both a shape to compare and a destination to land in. Within the same `Load()` the fold therefore runs before the adoption, which finds the spammer block already populated and skips on its existing guard (ConfigLoader.cs:206); a fold that could not be written leaves the adoption behaving exactly as it does today, so a machine still carrying pre-presets keys is carried forward either way. After a successful fold the legacy file is never read again, and the values it carried arrive from `local.yaml` from then on.
- If the fold **cannot be written** (read-only medium, full disk) nothing throws: the legacy file is read as a values layer for that session — the pre-fold behaviour kept as a fallback, not as the design — and the fold retries on the next launch.
- `local.yaml` is read as today, plus the `settings:` block holding the portable settings a save writes (step 1). Precedence, weakest source first: the shipped example, then the legacy layer (only before a successful fold, or on the fallback), then `local.yaml`.
- The active variant's dictionary resolves by name as today, and a missing one with an `.example` beside it is seeded from that `.example` verbatim; the `.example`'s `attributes:` key is `attributes: []` (step 3), so the seeded file keeps the switch's EMPTY semantics. With no `.example` the loud failure stays exactly as it is.
- The calibration PNGs, the OCR models and `docs/pet-data.csv` resolve as today.

**The fold's approximation, stated plainly.** It reads 'the player changed it' as 'it differs from the shipped example'. A release that changed a default under a key the player never touched cannot be told apart from an edit, so where the legacy file holds the old value the fold keeps it — the safe direction, the player's saved value winning over a silent behaviour change — and the release note that names the key is the habit that covers it. (The one recorded default change of this kind is `gem.empty_distance` 0.18 → 0.01. That key is not in the writer's projection — it lives in `local.yaml`'s machine block — so the fold never compares it; the 0.18 an install carries arrives through `local.yaml`'s seeded override, an existing channel this plan leaves alone.)

Moving to another PC is still copying the folder: everything the player owns stays under the application folder, so the exe, the models, the config and the calibration travel as one unit to a USB stick or a second PC — and the machine-bound parts (the calibrated coordinates, and the Windows pointer-precision setting no config file carries) still have to be re-checked there, exactly as today.

## 5. How an update works

The player's steps, in order, and nothing else:

1. Close the launcher (Windows holds the running exe open).
2. Download one file — `SealTools-vX.Y.zip` — from Releases. The firmware zip is needed only when the release notes say a reflash is needed (unchanged).
3. Extract the zip into the existing install folder and allow overwrite when Windows offers it. No exclusions, no files to copy, no comparing anything by hand. That is the whole update.
4. Run `SealTools.Launcher.exe`.

Why it is safe, mechanically: a merge-extract can only write files the archive contains, and the new public zip names no `local.yaml`, no `defaults.yaml`, no `attributes.us.yaml`, no `calib_*.png` and no log file. The two files an update used to cover leave the zip by name: the shipped defaults become `defaults.yaml.example` (nothing writes it; the player never edits it), and the US dictionary ships as `.example` only, seeded on demand. The first launch then folds the player's saved values into `local.yaml` — the portable ones into its `settings:` block, the spammer presets into the block they already had — as at most two once-only atomic writes done for them (the fold, and the preset adoption on a machine that never ran it). Measured today the zip has 19 entries; after the change it still has 19 — `config/defaults.yaml` leaves and `config/defaults.yaml.example` takes its place, `config/attributes.us.yaml` leaves and `docs/pet-data.csv` joins. One behaviour change rides in with `pet-data.csv`: with the feeding table present, the resident feeder reloads each row when the pet's own time line says it finishes rather than on the configured cycle — unless no species is named (`PetTool.cs:699-708`) — and the release note says so.

The cautious alternative also works: unzip beside the old folder, copy the **user-state files only** — `local.yaml`, `defaults.yaml`, `attributes.us.yaml` and the four `calib_*.png` — into the new `config/`, and extract the zip over the result; or extract first and copy them after. Either order is safe, because the zip names none of them; what makes it safe is copying only them. Do not copy the whole `config/` folder: it would also revert the previous release's program files — `attributes.yaml` and the `.example` templates all ship inside the zip (publish.bat:76, 78, 82). The same recipe is the sanctioned way to carry state into a fresh unzip, and it is what the old single-file recipe got wrong: copying '`local.yaml` only' silently dropped `calib_gem_result.png` and weakened empty-gem detection. Verify `local.yaml` and all four PNGs arrived before deleting the old folder; a missing `local.yaml` is re-seeded as a fresh v1 starting point with no error (§6.6).

The old instruction still ends in the same state if followed — 'except for `config\`' now errs in the harmless direction — so nobody has to unlearn anything to be safe.

On the first run after updating the player sees nothing happen and loses nothing: their saved values arrive through the fold — at most two once-only writes into their own `local.yaml`, done for them — and nothing else appears, moves or is deleted.

## 6. The migration requirement, as operations

These are the file operations that exist, in full. 'Migration' here is not an intention; it is a list that happens to be short.

1. **On an old install, the update performs no file operation on anything the player owns.** Extraction writes only program files, because those are the archive's members; the player's files are not read, moved or renamed by it. The first launch reads, and performs **at most two writes, both once-only and both through the atomic writer**: the existing spammer-preset adoption, only on a machine that never adopted its legacy presets (ConfigLoader.cs:225, reached from the guard at :206), and the fold, only where the example and the legacy file exist and the marker is unset. There is no seed, no copy, no rename, no backup file and no stamp, so there is no half state to interrupt and nothing to roll forward or back; a crash leaves only an ignorable `.tmp`.
2. **On a fresh install (or a fresh folder), exactly two seeding copies exist, and both are copy-never-move.** `local.yaml` seeds from `local.yaml.example` when absent — existing behaviour (ConfigLoader.cs:77-89). A variant dictionary seeds from its `.example` when absent — new in step 3, and it is the missing-file error's own instruction, automated. Each source stays in place; each destination is created only when absent.
3. **Every seed is idempotent and never overwrites; the fold is once-only and leaves its source alone.** The seed guard is the destination's existence, the same shape as the one-shot adoption guard already in the loader (`AdoptSpammerPresetsIntoLocal`, ConfigLoader.cs:204-226). The fold's guard is its marker — a modelled field inside `settings:` (`legacy_folded: true`), not a YAML comment or a bare document key, because the writers re-serialise from the object graph and would strip anything unmodelled; without the marker the fold would re-run on every load and re-impose old values over a newer release's defaults, so the marker is load-bearing. A modified `local.yaml` or a grown dictionary is never reset by a seed, and the fold never moves, writes or deletes `config/defaults.yaml` — it is the rollback copy and the record of what the player had. The marker is written even when the fold finds no differences, for the reason §4 gives. One edge the fold does not resolve, stated because it is a real state: a leaf the legacy file *does* carry but has deliberately cleared to an empty string is folded like any other difference, and the apply step may then drop it — `ApplyOverrides` mixes `!= null`, `IsNullOrEmpty` and `IsNullOrWhiteSpace` (ConfigLoader.cs:312, :335, :379) — which is exactly what happens to such a value today, so the fold preserves the existing behaviour rather than choosing a new one.
4. **Every write publishes atomically through the existing writer, under a gate that spans the whole read-modify-write** — a GUID-suffixed temp then `File.Move(overwrite)` (ConfigLoader.cs:439-456), with each writer re-reading `local.yaml` while holding the lock, applying its block and writing (the shape step 1 gives the 13 call sites outside the loader). The gate today locks only inside `WriteAtomically` (ConfigLoader.cs:441) while every caller loads outside it (LauncherService.cs:953 then :956; MainWindow.xaml.cs:1006/1015), so a pet-state write between another writer's load and its save can silently delete that writer's block; that gap is closed in step 1, because the fold adds a writer. The existing `local.yaml` seed is upgraded from `File.Copy` to the same writer while its tests are added, because `File.Copy` can leave a partial destination. The writer carries strings only (`File.WriteAllText` then `Move`); a future binary copy needs its own `File.Copy`-to-GUID-temp-and-`Move` sibling — no step here needs one.
5. **Failure is loud, in the existing shape — with the fold as the one stated exception.** A write that cannot happen (read-only stick, full disk) throws out of `Load`; the launcher's startup path shows no window and records the exception in `logs/error.log` beside the exe **when that file is writable — on a read-only medium there is no window, no message and no log** (App.xaml.cs:31-38 swallows its own logging failures). A drive that disappears mid-save takes the same path: the atomic write leaves no destination file, only an ignorable `.tmp`, and the failure is reported where the caller reports it. The fold alone does not throw: it falls back to reading the legacy file (§4). This plan adds no dialog surface.
6. **A `local.yaml` that disappears after its first creation is indistinguishable from a first run.** Quarantined by antivirus, dropped by an interrupted folder copy, hand-moved away, lost with a drive — the next launch re-seeds it from `local.yaml.example`, the player silently continues from v1 starting coordinates, the four calibration PNGs sit on disk making the install look calibrated, and no error is raised. This plan accepts that (no stamp, no backup, nothing in these steps can detect the loss); INSTALL.md says so. What makes the interrupted-copy case unlikely is §5's corrected recipe — copying and verifying the user-state files — not the re-seed behaviour. **Restoring an old folder has the mirror-image hazard, and it is the same rule that answers it.** A folder restored from a backup taken before the fold has no marker, so it folds against the *current* example: every default that changed across the releases it skipped is treated as the player's own edit and preserved, which is §4's approximation with more releases behind it — safe in direction, surprising in effect. A folder restored *piecemeal* — a `local.yaml` carrying the marker beside a `defaults.yaml` restored from an older backup — skips the fold and never reads the restored legacy values at all. So: restore or copy the configuration as one unit, and prefer a whole-folder restore from the same moment in time.
7. **Two installs, or two processes, on one config folder is unguarded.** The walk-up (unchanged) can bind a marker-less exe to an ancestor install's `config/` — the exe, a hand-moved copy or a folder whose extraction was interrupted; there is no single-instance lock; the save gate is in-process only; and the calibration PNG writers truncate in place (MainWindow.xaml.cs:3594, :3622, :4137), so the last save wins, images included. Do not keep a second copy inside an install's tree and run both, and do not run two launchers against one folder.
8. **Rollback to an older build loses nothing in the files.** Every user file is where it was: the update wrote only program members, and the fold wrote `local.yaml` only — `defaults.yaml` is byte-unchanged by the update and the first launch. The old build ignores the folded `settings:` block (`IgnoreUnmatchedProperties`, ConfigLoader.cs:21) and reads its values from `defaults.yaml` as always. Two cautions, stated plainly. Extracting the OLD zip over the folder rewrites `config/defaults.yaml` and `config/attributes.us.yaml` with the old release's copies — the zip carries all five config files — so keep copies of those two and restore them after the extract if they matter. And once the old build saves, its saves rewrite `defaults.yaml` as before and its `SaveLocal` drops the `settings:` block from `local.yaml`, so anything saved under the new build is invisible to it and is lost on its next local save; returning to the new build re-folds from `defaults.yaml` as it then stands. Roll back completely or not at all.
9. **The legacy file is kept and never written by the update or the fold, and is read only until it folds; after a successful fold, deleting it by hand is lossless.** Every saved value has been materialised into `local.yaml`'s `settings:` block, and the file is no longer read. Two things go with it, and the plan says them both: the fold's own record — the rollback copy of what the player had — and the root marker a build older than step 2 probes for (`FindRootDir` requires `config/defaults.yaml`, MainWindow.xaml.cs:10189). Step 2 widens the probe to accept either defaults name, so the deletion is safe only on a build at step 2 or later, and running a pre-step-2 build afterwards needs `defaults.yaml` back: restore a copy, or extract the old zip, which carries one. And once the fold has succeeded the file is not read, so an edit made to it afterwards — a hand-added key, a value changed back by hand — has no effect on anything, and deleting it loses that edit along with it.

**Adding a field, version to version.** An update is not the only thing that changes a configuration: a release can also ADD a key. Six measured facts decide the rule, and they come from the eight field additions this repo's history already contains (§10).

1. **A key a file does not carry takes the C# initialiser, and nothing has to add it.** This is the existing mechanism, and it is why most additions have been quiet and correct: `gem.empty_mode`, `empty_streak` and `tuner.ocr_retries` (9de8954), `tuner.spring_mode`/`mouse_guard`/`guard_px`/`recenter_max` (d5ff0f3), `pet.food_icon_png` (v2.12) and whole blocks like Quest (d285638) all reached existing installs with no migration and no hand edit. Nothing here changes that: the shipped example is the base and every update replaces it, so a key added to the example arrives on the next launch — and the fold does not interfere, because it writes only the leaves the legacy file actually contains.
2. **A key with no safe default has no mechanism at all, and naming that is the point.** Where a property has no initialiser the value is the CLR default — 0, "", false, an empty list — silently. `reference_window.width`/`height`, the four hotkeys, `tuner.timing.*`, `max_retries` and `arduino.baud` are in that class today. So a release that adds a field whose correct value cannot be defaulted MUST add a `ConfigValidator` rule with a message naming the key and the tab to open. That is a release-time obligation no plan can automate; what this one does is state it, because the alternative is a silent zero.
3. **The recorded damage was on the WRITE side, not the read side.** Every field-addition loss in this repo is a new key missing from a projection that rewrites a file: `ocr_retries` 3 → 0, quietly disabling the OCR re-scan; `gem.move_mode` reset on every save; a hand-added `pet:` block deleted; a whole spammer block deleted; and `LocalPetSlot.PetSlotEmptyPng` dropped, which on a live run read three empty rows as occupied and started an empty boarding. The fence matters more than the arrival.
4. **The fence must cover every hop a portable key crosses, and there are four.** `SaveSettings`' projection → the mirror's fields on `LocalOverrides.Settings` → the fold's read list → the if-present lines in `ApplyOverrides`. Step 1 fences the first two; a key missing from either of the last two is written to the file and silently DISCARDED on every load, which is exactly the recorded `FeederCountLeftFraction`/`FeederCountMinScore` bug. Step 2 extends the one fence over all four hops.
5. **A rename is not an addition.** `IgnoreUnmatchedProperties` ignores the old key and the next save deletes it, so a rename needs a hand-written pass; four exist (`MigratePetSlots`, `MigrateSpammerPresets`, the `startup_step` fold, the variant resolution) and they are the shape to copy. Under this plan a rename has one extra requirement: the migration reads `local.yaml`, because after the fold that is where the player's value lives — `config/defaults.yaml` is not read any more.
6. **A new MACHINE-SPECIFIC key is never carried to an existing install, deliberately.** Nothing in these steps writes `local.yaml` from a release: the fold writes only portable values the player had changed, and a seed never overwrites a file that exists. Such a key arrives as its class default and the player calibrates it — which is what happens today, and what the calibrators are for.

The seventh case is a changed default under a key the player never touched, and §4 states it: where the legacy file holds a value the fold keeps it, the direction is the safe one, and the release note naming the key is the habit that covers it.

## 7. The sequence

Each step is independently shippable. Only step 3 is visible to a player; steps 1 and 2 are inert under the old packaging.

| # | Step | Size | Player-visible change | Verified by |
|---|---|---|---|---|
| **1** | A `settings:` block in `local.yaml`, and a writer shape that can set it safely | M | none | 5 new tests — a projection fence, a round-trip, a byte-equality, the serialisation-shape test, the stale-writer interleave — plus the existing suite (240 methods / 292 executed cases) |
| **2** | The loader reads a shipped base, folds the legacy values once, and accepts either root marker | M | none (inert until the zip changes) | the four fold tests, the legacy-layer fence, the precedence test, the update rehearsal, the today-shape regression fence, the root-marker predicate |
| **3** | The update zip stops carrying anything a player owns | M | yes, once: the update procedure loses its exclusions; a fresh US switch works without a hand copy; the feeding table works, and the feeder follows it | seed tests both directions, the new `publish.bat` scan test (reads the script and asserts its member list equals the declared program list), the zip allow-list assertion, the value-neutral diff, both rehearsals (extract-over and user-state copy) |
| **4** | The launcher stops rewriting a shipped file | S | none directly; the visible sign is that updates can no longer reset settings | switch-writes-only-local (loader-level proxy), no-`active`-key, adoption retarget, rollback-compat; the build gate proves no caller survives once the six test call sites are moved |
| **5** | Saves stop pruning what they do not own | S | additive | the existing fences stay green, plus 2 new tests |

**Step 1 — a `settings:` block in `local.yaml`, and a writer shape that can set it safely.** `ConfigLoader` gains a `settings:` block on `LocalOverrides`: a nullable mirror of exactly what `SaveDefaults`' projection writes — window, reference_window, game (variant and variants named explicitly, never the resolved object), arduino vid/pid/baud, hotkeys, the 13 tuner fields, the 7 gem fields, the 2 pet scalars; spammer stays excluded, and the `legacy_folded` marker is a modelled field of the block (step 2 writes it; every writer must carry it through untouched). `ApplyOverrides` gains the if-present lines that apply it. **Where the directions disagreed, and which consideration won.**

1. Move versus no move. The relocation direction argued a `profile/` folder beside `config/` satisfies the fixed constraint (it is still under the root). No move won: an update can cover a file because the archive contains it, not because of which folder it lives in — safety comes from the member list and the writer targets — and a move would add a migration, a new folder name and a doc sweep for no additional protection. Relocating outside the root was rejected directly by the player's constraint (§8).
2. Schema stamp versus shape detection. Two directions proposed on-disk version stamps. Shape detection won, and the fold keeps it: the old state is detected by existence and difference — `defaults.yaml` beside the example, values that differ — not by a version key, and the fold's one marker (`settings.legacy_folded`) is a modelled field the existing writers carry, not a stamp the object-graph writers would strip. Every migration the repo already has detects the old state by absence (`local.Spammer != null`, ConfigLoader.cs:206; `pet.Slots.Count > 0`, :140), and the stamp proposals would have lied in exactly the window they claimed to guard.
3. Banner versus run gate. The fingerprint direction proposed refusing to run unguarded on a mismatch. The banner won: the gate is click-through ('Run anyway'), it would nag the deliberate USB-stick user, and the launcher's gate surface has no automated coverage. Visibility is the honest part; enforcement without teeth is not.
4. 'Only `.example` files in the zip' versus shipping live `attributes.yaml`. The real invariant won: no member is a file the app writes or the player is told to grow in place. `attributes.yaml` is release-maintained program content that no writer targets; the assertion encodes the allow-list of program files and the `config/` name rule, so the rule and the list cannot drift apart.
5. `pet-data.csv` optional versus mandatory. Mandatory won (see the second kept piece above).

## 8. Non-goals

- **Not a v3.** Every step lands shippably and only one is visible; this is v2.x work.
- **Nothing outside the application folder.** Relocating the player's files to `%APPDATA%` or anywhere else was considered and rejected on the player's fixed constraint (2026-10-13): the config stays at the same root path so the folder stays easy to move. The promise 'There is no installer and nothing is written outside the folder' (INSTALL.md:95-96) binds.
- **Not a `profile/` folder inside the root either.** Moving the live files into a subfolder beside `config/` — the direction PLAN-PATHS.md's §4 and step D proposed — was examined and declined: it satisfies the letter of the constraint but buys no safety, and it would add a migration, a folder name and a docs sweep for the same outcome. Its diagnosis (the classification, defaults.yaml-as-user-state, the fear of losing the calibration on the first post-change run) is kept; its relocation is not.
- **No schema stamp, no manifest file, no export/import format.** The repo's migrations detect old state by shape; the fold's one marker is a modelled field inside `local.yaml` that every writer carries, not a stamp on a source file; export/import is real work no step here needs.
- **Not the OCR model embedding** (IDEAS.md §6) **and not the Launcher extraction** (ANALYSIS-UI.md §5) — both owned elsewhere.
- **Not a fix for the project's field-list discipline.** `SaveSettings` writes a fixed list and the fold reads one; a portable key added later must be added to both and their fences, or the fence fails the build. The prune-what-you-do-not-own problem is step 5, deliberately scoped on its own.
- **Not a log-retention policy.** `logs/reads/` was measured at 3,373 files / 5.9 GB on one dev machine, and growing; nothing cleans it; that is its own problem.
- **Not a firmware change.** Nothing here touches the sketch, so no step needs a reflash; the release notes should say so.

## 9. Open questions for the player

1. **Confirm the fold: a once-only write on the first launch after the update.** The plan is written for it — the first launch of the updated build compares the legacy `defaults.yaml` with the shipped example and writes only the differences into `local.yaml` (portable leaves into `settings:`, spammer presets into the block they already had), once, then never reads the file again. On a machine that also never adopted its legacy spammer presets the existing adoption is a second once-only write in the same launch; both are atomic, both are guarded, and both leave their source alone. Options: (a) fold once, as planned, recommended — the write is atomic, once-only, the file itself is untouched, unchanged keys keep tracking the released template, and deleting the legacy file afterwards is genuinely lossless; or (b) keep `defaults.yaml` forever as a values layer: no write at all, but every portable key it holds keeps shadowing every future default change, and the file must never be deleted. The plan needs this verdict before step 3 ships. Two consequences are stated with it, so they are not surprises: a release that changed a default under a key you never touched is preserved (the fold cannot tell it from an edit — the safe direction, with the release note naming the key), and if the fold cannot be written that launch keeps reading the file and retries next time.
2. **Does the repo keep tracking the empty `config/attributes.us.yaml`?** After step 3 the shipped US dictionary is `attributes.us.yaml.example`. Measured: the tracked `attributes.us.yaml` parses to the empty LIST (`attributes: []`, :19) that the switch's EMPTY semantics is written against, while the `.example` currently parses to a NULL list (`attributes:`, :31, only commented-out entries) — which is why step 3 changes the `.example`'s key to `attributes: []` in the same commit that rewrites its header, so the verbatim seed keeps EMPTY semantics and the retargeted test holds. Options — (a) remove the tracked file, add a gitignore rule, let the dev tree seed it exactly as an install does, and point `TheShippedUsDictionaryExistsAndIsEmptyOnPurpose` (ConfigLoaderTests.cs:505-518) at the `.example`, recommended for one lifecycle; or (b) keep tracking it as the dev tree's live dictionary and update its header text. Step 3's commit needs this answer.
3. **Should the mismatch line also carry the Windows pointer-precision setting?** 'Enhance pointer precision' (CALIBRATION.md:165-177) changes what the hand-tuned HID counts mean and lives in the registry, not in any config file. Step 6 could read it (read-only) and name it when it differs from what was set at calibration time, at the cost of one more stored value and one more startup read. Recommended: leave it out for now — the docs warn about it and a recalibration is required anyway — but decide before step 6 ships if the drift shows up in practice.
